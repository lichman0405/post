# POST V2：执行方式比较与工期估计

日期：2026-10-26；规划估计，不是模型基准或交付承诺。

## 1. 推荐执行方式

| 方式 | 优点 | 代价／限制 | 本项目建议 |
|---|---|---|---|
| 一个 Agent，兼任业务编码、验收与 Git 控制，不使用 subagent | 调度简单、没有多 worktree 写冲突 | 所有工作串行，长上下文漂移与自证风险集中；会改变本仓库角色和独立验收规则 | 不作为当前交接默认；没有因取消 drive 获得改用此模式的授权 |
| 长期 Supervisor＋独立 Claude Code Worker | 最小任务上下文、隔离、独立验收、可按模块并行，沿用仓库已有机制 | 需要 Supervisor 持续判断，承担合成／Review／Gate 和进程恢复 | 推荐；先一个 Worker 实测，再按无冲突任务扩大到 2–3，硬上限 4 |
| 上一行再加可选 drive | 可减少机械调度操作，有已有状态／心跳／接管能力 | drive 不能独立解决所有返工／CI／规格判断，也不是产品依赖 | 按 Owner 决定可选；主方案由 Supervisor 直接编排子命令 |

独立 Worker 不是 Claude Code subagent。取消 `rddev drive` 的硬约束不需要删除工具、不要求重写整个 orchestrator，也没有取消独立验收和 Git 权限边界。

## 2. 时间估计

目标：已确认全部 V2 功能、真实网页验收和可部署团队试用包。以已有后端可以较多复用、Ubuntu／凭据／模型／GitHub 权限齐全、一天 24 小时可持续运行、Supervisor 与 2–3 个独立 Worker 为条件：

| 情况 | 日历时间估计 | 解释 |
|---|---|---|
| 顺利 | 2–3 周 | 主要缺 UI 接线；Git/RSG、上传、模板／分析后端和现有 Gate 无重大阻塞 |
| 建议预留 | **3–5 周** | 包含契约补齐、真实 UI 集成、正常返工、CI 与部署恢复修复 |
| 返工较多 | 6–8 周或更长 | Kimi/CLI 特性不兼容、后端关键链缺失、共享 Gate／状态问题或复杂跨模块返工 |

这不是按 token 每秒换算。31 个工作包的逐项粗估合计 **388–812 个串行智能体工作小时**，数字见 [estimate.json](../tasks/v2/estimate.json)，不等同人工工时，也没有在本仓库对 Kimi 实测。

用于检查数量级的假设：有效并发约 1.5–2.0（依赖和验收会串行），另加 48–96 小时集成／CI／恢复等待，再加 25%–50% 返工余量。由此得到约 12.6–39.8 天的粗范围；考虑不确定性，建议用 3–5 周安排，不把粗范围上限视为保证。

## 3. 哪些时间不能保证

完全零人工无法保证一个确定完工日期。新的 L3 决策、重大架构冲突、缺凭据／额度／GitHub 权限等可能使路径一直等待；模型速度不能消除这些等待。操作系统稳定、会话能恢复、费用额度和已有授权是持续运行前提。

上述时间指“工程可部署试用”。真实团队实际使用、科研结论确认与反馈周期由人决定，不计作已经自动完成；也不要求为了获得使用反馈而假装产品还不能交付。

首 3–5 个真实交付切片完成后，必须用 Worker 周期、返工率、G2/G3/CI 时长、关键路径和模型工具成功率重估。若相差较大，更新 estimate 与 progress，不能反过来降低验收满足原日期。

## 4. 最高风险项

1. 网页语义变更到 Gitea ref／RSG 合并的一致性；旧测试用 CLI Git 准备过关键提交。
2. 新 Blob 上传、受限下载、版本和发布影响清单贯通，包含大文件／分片与资源限制。
3. 个人自审与团队独立评审 policy、历史兼容、权限负向。
4. 项目模板版本和分析结果的来源／参数／数据版本，不得覆盖历史。
5. 真浏览器测试从空业务空间走全链、正常入口可达，不能靠 API/helper 或 seed 缺失入口。
6. Kimi 的工具／RESULT／Review／恢复兼容与持续 Supervisor，不把 drive alive 或 CLI exit 0 当产品完成。
