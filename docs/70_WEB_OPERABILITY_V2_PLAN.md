## 1. 目标与已确认方向

**平台定位校正（D13）：POST 是类似 GitHub 的科研项目托管与版本化协作平台。核心流程由使用者主动操作；撤回将 AI 自动整理、生成研究记录或解读科研内容作为产品默认的假设。可选 AI／Agent 整合不作以下核心任务的前置条件。**

**主要内容入口（D14，Owner 已选 A）：研究问题、实验、资料、结论与证据为项目主要入口，代码和档案与它们关联。Web 导航、版本差异与 PR 优先呈现科研内容变更。**

**编辑方式（D15，Owner 已选 A）：使用者可先用少量信息保存研究草稿，逐步补充内容；送审与发布前按各阶段要求检查完整性。身份、权限、版本及基本有效性约束仍须成立。**

**新项目默认（D16，Owner 已选 B）：新建项目默认 Public，建立时可选 Private；既有组织政策仍须遵守并在 UI 说明。此决定不更改既有项目，不推定附件下载／使用权，也不代替任何 private→public 确认。**

**公开附件默认（D17，Owner 已选 A）：公开项目新增附件的上传界面默认 Open，清楚显示访客可下载，提交前可改 Restricted；更严的既有政策仍适用。私有项目及既有受限附件不因此开放。Restricted→Open 需明确确认，下载存取与使用授权分开处理。**

**模板与字段（D18，Owner 已选 A）：提供默认科研模板，允许项目配置补充字段；核心身份、版本、权限和证据规则统一。模板自身需要可追溯，变更不能就地改写历史研究记录或 Release。新增 WEB-26/U12 纳入 V2 验收。**

**审核与合并（D10／R1，Owner 已确认 A）：个人项目允许有权作者明确自审并合并自己的 PR，团队项目可要求独立评审。仍须遵守必要检查与更严格的组织政策，保留审计和版本历史；自审不标为独立验证，不静默放宽既有策略。**

**数据查看与分析（D06／R2，Owner 已确认 A＋B）：V2 同时交付通用预览／下载与用户主动操作的基础作图、统计、曲线拟合；两者均纳入最终 Gate。结果显式保存并关联源数据版本与参数，原始数据不变；不默认 AI 判断或生成科研结论。新增 WEB-27/U13。**

**领域范围（D19／R3，Owner 已选 A）：定位为通用科研平台，提供通用科研模板与项目补充字段；首批重点做好材料科学模板及 synthetic MOF 案例。平台入口、权限与版本协作不限定材料科学，也不把领域样板理解为所有学科专业算法或专项合规能力已完成。**

让研究者从正常网页入口完成：注册／登入 → 建立团队与项目 → 规划研究 → 记录实验／计算与证据 → 提交变更 → 评审与处理冲突 → 合并 → Release → 选择性发布 → 他人发现、重用、回传证据 → 贡献归属。

**交付目标（D12/R4）：可部署、功能完整的团队试用版。包含全部已选功能、真服务、完整网页验收、部署、备份恢复和运维文档；本轮不承诺面向公众运营的 Beta。工程交付可自动验收，团队真实科研试用意见另行记录，不伪造人工签收。**

**开发执行（D20）：保留长期 Supervisor＋独立完整 Claude Code Worker，不使用 subagent；Supervisor 直接编排现有 rddev 子命令。rddev drive 可选，不是启动条件。完整 GitHub 交付链和 G1–G4 保留。**

Owner 已确认：

- 验收必须从网页实际操作完整流程，不能以直接调 API 代替。
- 第一批使用者先是 owner 或一个团队，再逐步邀请合作者。
- V2 同时支援日常项目工作与正式成果协作：使用者主动管理计画、记录、Issues、内容版本与成果。依 D13，这不表示平台自动替使用者产生或解读研究内容。
- 日常研究先提供计画、执行记录、结果上传与外部任务连结；实验和计算继续在既有工具执行。自建执行引擎、启动外部计算、控制仪器不列入这一轮已确认范围。

建议的交付次序是「单人可用 → 团队可协作 → 成果可重用 → 跨团队网络」。跨团队闭环仍是最终目标；早期里程碑只交付其中一段时，须明确标示尚未完成的后续流程。

## 4. 任务优先顺序与依赖

P0＝单团队完整主流程或验收可信度的必要条件；P1＝原始开放网络闭环的必要工作，仍是本计划最终交付必需；P2＝V2 待选扩展。此处 P0/P1 是优先级，不是原仓库 P0–P13 阶段。

每个 WEB 任务须含契约盘点、产品 UI、必要后端、权限、业务结果与 browser 测试，避免把「画面完成」与「后端接线」拆成两个互相宣称完成的任务。表中的 acceptance 都按第 6 节执行。

| 任务 | 优先级 | 交付与涵盖缺口 | 直接依赖 | 可判定的网页验收 |
|---|---|---|---|---|
| WEB-00 基准与契约盘点 | P0 | 锁定 commit、路由／角色／动作清单、G01–G27 逐格证据；先查 G07、首次发布、附件下载的后端断点 | 无 | 每个承诺动作都有 UI 入口、服务契约、情境编号；缺口标为未通，不能用历史绿灯代填 |
| WEB-01 真实 UI 验收框架 | P0 | 隔离真服务、browser 驱动、CI 作业、证据与反绕过规则；G23 | WEB-00、WEB-28 | 登入可由 DOM 操作完成；故意断开一个主按钮后测试红；缺依赖、缺账号建立入口、未执行任一步均 fail |

## 6. 网页实际操作验收规则（本轮硬性要求）

### 6.1 什么才算完成一步

1. 从使用者可见的首页、列表、内容页或通知连结进入。账号、项目、对象、draft、PR、Release 等本轮业务实体由对应 Web 流程产生。
2. 操作者使用 DOM 可见控制：点击、键盘、填表、选项、档案选择器、确认、取消、浏览器下载。应用本身正常透过 HTTP 存取 Go API。
3. 页面显示结果与下一步；刷新、重登入或第二会话重开后仍正确。只看到成功 toast 不算完成。
4. 网页改动触发的资料、Git、blob、审计和事件正确。只读后端检查可补强证据，但不能用来代替画面上的成功与持久化验证。

### 6.2 禁止的替代方式

- 在测试里用 `page.evaluate(() => fetch(...))`、`page.request`、`APIRequestContext`、curl 或脚本替使用者注册、建项目、写对象、送审、评审、合并、发布、fork、订阅等。
- 测试透过 SQL、fixture helper、直接存储写入或 CLI Git，代做旅程中应由使用者完成的业务状态。
- 预灌已合并 PR／已发布 Asset 来证明「首次合并／首次发布」可用；手工拼 candidate query、UUID 或深连结以绕过缺失入口。
- 拦截真服务写请求并返回假成功、修改 browser storage 取得身份、注入结果进 React state、以 API 流程通过冒充 UI 通过。

### 6.3 允许的环境准备与辅助

- 启动真 PostgreSQL/Gitea/MinIO/Redis/API/Web/worker、套用 migration、清空隔离测试空间、安装固定测试参考 schema，准备明确 synthetic 的本地档案输入。
- 测试账号由网页注册或产品支援的真实登入流程建立。若采用邀请／验证邮件，在隔离邮件收件匣用可见连结完成；不能用 API 植入 session。
- 可另有 seed demo 用于快速 smoke／截图；它不得出现在「由空项目完成产品全流程」的唯一证明中。
- 只读网路观察、DB/Git/blob 检查、log correlation 与下载内容核对作为附加证据。专用 API／permission negative tests 继续保留，但独立标示，不能为缺失 Web 步骤补票。
- 故障注入可控制服务可用性或网路失败；使用者的业务动作与恢复仍经网页完成。
- Agent／MCP 整合可有另行端到端测试；本轮 UI 核心旅程不能把 CLI Agent 指令当成 Web 研究编辑的替代。

### 6.4 证据与判定

- 每次记录：commit SHA、实际 runtime／schema 版本、环境、run id、角色、入口 URL、步骤、输入摘要、预期／实际结果、时间。
- 真服务启动和关键 background consumers 均需检查；缺工具／服务／migration／任一步骤立即 fail，不默默 skip，不用任意增加 timeout 掩盖错误。
- 每条旅程提供 browser trace、关键步骤截图、console／network 错误、业务实体版本引用。只在确定 synthetic 的测试环境录 trace；真实试点资料证据须最小化与去敏，不能记凭证。
- WEB-01 的检查器审查旅程程序与共用 helper 的 API／存储／CLI 旁路；静态扫描只是辅助，Supervisor 同时审查 trace、真实服务与步骤结果。新 helper 也须纳入审查。
- 首次验收新增至少一条反例：断开核心按钮的 handler 或去掉其导航，对应 UI 旅程必须红；还原后绿，证明没有偷偷从 helper 完成。
- CI 上有真实执行入口且为 blocking；与 `specs/orchestrator/gates.json`、G2/G4、工作流和任务测试帐本同步。作业名称在接线时确认，不能只交付没人跑的脚本。
- 功能实现的四层 Gate 仍需通过；本计划新增 Web 操作证据，不删、不跳过、不弱化既有安全／不变量测试。

## 7. 完整验收旅程

共通前置：乾净隔离资料、真服务、正常首页。角色 A 为第一团队 owner，B 为内部 Contributor，C 为审查者，V 为 Viewer，E 为原团队非成员的外部贡献者，N 为匿名。账号与角色依 U01/U02 从 UI 建立；E 在自己的团队／项目工作，不藉加入 A 的团队来绕过外部贡献路径。同一故事使用多个独立 browser context。

每条旅程除明列结果，还须验证重新载入后仍然成立。

U03 等情境中的「记录、建立对象、建立 Evidence」均指使用者主动填写、选择关联与提交。档案上传不默认触发 AI 建立科研内容；所有核心 U 情境都须在没有 AI provider／Agent 的情况下成立。

### U01 — 新使用者到第一个项目

1. N 打开首页，由可见入口进入注册，填资料建立 A；错误资料显示字段错误。
2. A 登入后看到建立／继续研究入口；建立页默认 Public，A 明确切换 Private 后建立有 purpose 的 Private Project。个人试用与团队归属均按既有 policy 执行。
3. 检视新项目的空状态，建立第一个研究问题与路径的入口清楚可达。
4. 再使用默认 Public 建立公开项目；在两者切换、登出重登入、在全新匿名视窗查看。后续外部贡献主故事以这个公开项目为来源；私有项目保留作隔离与选择性发布案例。原有私有项目不因新建页默认而改变可见性。
5. 同 slug 重复建立被拒且无第二份项目；私有名称／内容在匿名结果中不可见。

### U02 — 团队、成员与工作事项

1. A 建立组织；B/C/V 由网页注册或受邀进入，A 经管理页授予不同角色。
2. A 建 Issue／研究待办，指派 B 并连到一个研究问题；B 进入、回复、修改工作状态。
3. V 不能编辑、送审、合并或提权；提示与操作规则一致。
4. B 更新自己的 Profile；角色与 affiliation 变更不抹除既有署名与个人历史。
5. 另一项目不出现相同硬编码 Issue；一笔研究待办完成不把 Question 自动判为已解决。

### U03 — 日常研究到可审查变更

1. A 在项目提出研究问题，建立计画；选明确的研究 branch，记录假设、材料／样品与 Protocol 版本。
2. B 记录一次 Experiment 或 Calculation 的目的、条件、负责人、执行过程与外部 run 连结；包括一份失败结果。
3. 从记录附挂输出、建立 Dataset，补观察、限制与来源；交接给 C 后 C 能由任务找到完整上下文。
4. 建立具 scope 的 Claim/Finding、支持与反驳 Evidence Assertion；从 Evidence 点回原始对象与版本，Provenance 另行呈现。
5. 存储研究变更与提交说明；切分支、看旧版／差异，确认 main 尚未被改写。
6. 由正常 Web 操作形成可以交给 PR 的真实 Git／RSG 状态；全程不需要命令列补提交。
7. 独立案例覆盖 V1 全部 12 类 Scientific Object 的建立、版本、必要字段与关联；不以单一 happy path 宣称全型别完成。
8. 依 D15，先只填标题、简述等该类型的最小草稿信息并保存，离页／重登入后可继续；补充条件、方法与证据时保留正确历史。正式动作所需字段未齐时列出可理解的缺项，补齐后可回到原流程；不因草稿信息不足丢弃已填内容。

### U04 — 附件、资料存取与恢复

1. 从公开项目 Experiment／Calculation／Dataset 的附件栏选择 synthetic 档案，确认上传界面默认 Open 且说明访客可下载；上传并附挂到具体研究版本，匿名访客由正常页面成功下载。另在私有项目上传时，确认附件不因公开项目的新默认而开放。
2. 中断一次上传再重试；成功后重新登入，由对象页预览／下载，内容 hash 与输入一致。
3. 补交修正版档案形成新版本；过去对象／Release 引用仍指旧档。
4. 在公开项目上传第二个附件时主动选 Restricted；metadata 可公开而 blob 保持受限，以匿名及无权账号从页面尝试开启／下载时被拒，有权账号仍可取回。D17 不改既有受限附件；Restricted→Open 须有权者明确确认，取消时维持原权限。下载开放不改写 rights 声明。
5. Files 页持续只有阅读、历史与允许的下载；附件上传不产生 Files 编辑／删除捷径。
6. 精确大小／类型／配额／长期存取政策在 D06 裁定后纳入边界案例，未裁定前不得宣称整条已验收。

### U05 — PR、评审、冲突、合并与历史

1. A/B 建立两个研究 branch，从网页对同一 Protocol 做出有科学差异的版本，形成真实冲突。
2. B 由分支页建 PR、检查 diff／checks 并送审；reviewer 在通知／待办中找到它。
3. C 分别做 Scientific／Integrity Review，先要求修改；B 从网页补件并重送，过期的评审按既定规则处理。
4. 从 PR 进入冲突页，选择明确的人类处置并填理由；回到 PR 看到最新状态与 checks。
5. 未满要求时 merge 不可执行且原因可见；满足条件后 A 点击合并。
6. 主线、PR 结果、Git ref 与科研状态一致，Activity 显示 actor/via／原因；重复点击不重复接受或记贡献。
7. 从治理页对接受对象提出 Abort 再 Reopen，按权限／review 流程完成；旧版、理由、原始资料持续可查。
8. 另建带有敏感测试标记的 private branch，将其中选定内容送往 public main 时走独立 publication gate；先取消、再只确认列出的对象。匿名可见范围与预览一致，完整 private branch 历史和未选内容仍不可见。
9. Git 暂不可用时不得显示整体完成；恢复后由页面支援的操作重试，不靠人手修 DB/Git。
10. 不完整草稿送审时，显示相应必需信息与补正入口；依规格补齐后重新送审成功。能保存草稿不代表可以越过 Review、Merge 或 Publish 门槛。
11. 单独建立只有 A 的个人项目，由网页提交 PR、明确完成作者自审并合并；记录显示作者自审，保留必要检查与历史。团队项目配置独立评审后，同一作者不能以自审替代他人批准；更严格的组织政策仍生效，既有政策不因升级被放宽。

### U06 — Release 与第一次发布四类 Asset

1. A 从 U05 真实合并后的状态建立 Release，检视 pinned 版本、hash、review／policy 与 manifest。
2. 从该 Release／accepted 内容选「发布为 Asset」，填 metadata、creators、rights、版本与 blob access。
3. 逐项检视影响清单，先取消一次确认未公开；再次确认后由结果页打开公开固定版本。
4. Dataset、Protocol、Material Collection、Benchmark 各有独立成功与必填失败验收；主故事至少两类真实参与重用。
5. 新增后续研究版本并建新 Release／Asset version，旧版内容与身份不变；metadata revision 与 scientific version 区分。
6. 由页面导出研究包／manifest，核对版本、Git SHA、blob hash 与 policy pins；新项目没有预先存在的 Asset 也能完成首次发布。

### U07 — 公开知识与匿名发现

1. A 选择某个已接受的 Finding／Claim，预览并确认发布特定版本；私有证据与分支历史不自动公开。
2. N 从首页／Explore 找到该成果，开启知识页、证据、作者与组织，再返回来源。
3. public 内容匿名可读；restricted blob／未公开内容不泄漏。目录仅列既有允许公开的实体，attestation 仍按既定 pid-only 范围，不扩大私有实体的发现面。

### U08 — Search 到新研究项目

1. 已登入 B 在搜寻框提出能命中 U07 本轮发布内容的问题，看到来源及确定版本；没有来源时看到明确限制。
2. 点「开始研究项目」，选来源与目标归属，预览／修改 Draft Research Context。
3. 取消一次确认无正式初始研究状态；回来确认后由结果页进入新项目，研究问题及来源可追溯。
4. 刷新／返回／重按不多建项目或重复初始研究状态；私有参考不被带入不允许的项目。

### U09 — 外部重用、验证与回馈

1. E 作为原项目非成员，从公开成果或贡献机会找到明确可做的验证任务。
2. E 选固定版本 Reference／Dependency 或 Fork/Derive，建立自己的项目／研究路径；页面保留 origin、rights、lineage。
3. E 经 U03/U04 记录独立验证或相反结果，建立 external evidence，从网页提交外部 PR／贡献提案。
4. A 经正常评审／合并接受，双方页面显示 reviewed／unreviewed／origin 状态；E 不能直接写 A 的 main。
5. 不同科学结论可保持 contested；原团队不能把不利证据从历史静默删掉。

### U10 — 贡献、订阅与依赖变更

1. A/E 从页面 Watch 对方的相关项目／Asset，选事件偏好；A 发布一个新的上游版本或标记问题。
2. E 的 Inbox 出现本轮真实事件与依赖影响警报，点击可到正确对象／版本并做明确处置。
3. 不自动升级依赖或替人修改 Claim；退订后不再产生其不想接收的后续通知。
4. 接受贡献的事件在 E 个人 Profile 可追溯到 PR／Release／Evidence，重试不重记；E 离开自己的组织后个人历史仍存在。

### U11 — 权限、政策与故障的可用性

1. 用匿名、Viewer、Contributor、Reviewer、Maintainer／Owner 的独立会话走相同内容入口；可见操作与权限一致。
2. 在页面更改有效 policy／review 要求后，新提案依新规则，历史 Release 保留旧 pins；最后一位 Owner 不能被不当移除。
3. session 过期、断网、服务错误、已失效版本、空列表、保存重复提交都可理解并可恢复；不丢未提交内容、不泄漏私有存在性。
4. 用键盘完成建立、评审、发布核心表单；核心页有资料状态下检查 a11y，中英文主要操作可理解。
5. 按原始选择性 Publish 与 D16/D17 验证成功／取消／拒绝；整体项目可见性切换及新 attestation 发现面不列本轮新增功能，不由实现擅自扩大公开范围。

### U12 — 项目模板与自定义字段（补充第 7 节验收旅程）

1. A 从项目设置选择默认 Experiment 模板，增加一个项目补充字段，例如 synthetic MOF 案例的相对湿度、单位及说明；保存后从正常入口重新打开。
2. B 在该项目创建实验记录，使用新字段保存草稿并补全记录；刷新后数值和单位正确，在提交／PR 中能看到相应变更。
3. 在另一个项目创建同类记录，不受前一项目的字段配置污染；未授权用户不能修改模板或绕过核心字段规则。
4. 更新模板，确认既有记录、旧版本及 Release 仍按其原模板／字段含义显示；新记录使用新版本。若需要迁移已有内容，必须是单独显式操作并留历史，不后台覆盖。
5. 错误类型或不合阶段要求的值显示可理解错误，已填内容保留；草稿与送审／发布门槛遵守 D15。
6. 全部配置、录入、提交、检查均经网页完成，不通过 API 或数据库预灌模板代行。
7. 依 D19，除完整材料科学／MOF 故事外，再由网页用通用研究模板建立一个不含材料领域专属必填项的项目，增加补充字段、创建记录并完成 PR／评审／合并。确认产品导航和共享规则不依赖材料专属术语；此案例验证通用平台能力，不冒称完成该领域全部专业功能。

### U13 — 数据预览、主动分析与结果追溯

1. 从本轮经网页上传的附件打开文本／Markdown／PDF／图片／CSV 或表格，检查可读预览与原件下载；选中一个固定版本的 synthetic 数据集进入分析页。
2. 用户主动选择数据列、单位、数据范围及处理选项，创建基础图表、查看基础统计、选择支持的曲线拟合方法并执行；显示有效样本范围、参数及必要的拟合结果信息，不替用户判断科学结论。
3. 使用预先确定的数值参考数据检查统计／拟合结果及图中数据对应关系；另外覆盖缺失值、非数值列、样本不足、单位／维度不匹配和拟合失败，错误有说明且不伪造成功结果。数值正确性还需独立 unit/integration 测试补强，不能只看图形存在。
4. 用户点击保存结果，保留源 Dataset／附件的固定版本、所选列／范围、处理规则、方法／参数、实现版本及操作者。结果可按既有科研模型形成可审查的派生内容；具体模型映射在契约设计时明确，不静默新增对象类型。
5. 重登入后从研究内容打开保存的分析，能查看并复现相同设置、下载图表与结果；源数据出现新版本后，旧分析仍指原版本。更改分析设置保存为新版本，不覆盖原始数据、历史分析或 Release。
6. 受限源数据的分析和导出遵守既有权限；结果不得通过预览、缓存或导出绕过数据访问与发布门槛。全过程使用网页，不经脚本直接创建分析结果；查看数据不触发 AI 生成科研记录。

### U14 — 新环境部署、升级与恢复

1. 运维准备允许使用 CLI：在隔离的干净 Ubuntu 24.04 / WSL2 Linux 文件系统按 runbook 配置真服务、固定版本依赖、迁移与启动；不注入替用户完成的业务实体。
2. 从浏览器首页注册并完成核心研究、PR、Release、Asset、附件与保存分析等流程，核对构建 SHA／schema 版本；这些业务对象必须来自正常网页操作。
3. 按文档备份 PostgreSQL、Gitea、Blob 及必要配置元数据，在另一个空环境恢复；备份／恢复是运维动作，不是代做业务步骤。
4. 重新登录网页，检查项目、旧版本、PR、Release、Asset、研究证据、模板、分析记录；下载内容 hash 正确，私有和 Restricted 权限不扩大。
5. 通过文档支持的版本升级／应用回滚演练；数据库采用受审迁移与 forward repair，不能私自手改生产 SQL。错误版本／缺配置／服务不可用均有明确诊断。
6. 提供安装、升级、备份、恢复、问题排查、已知限制和团队试用步骤。工程可交付状态与真实团队使用反馈分开，不把没有发生的人工试用写为通过。

## 11. V2 首批功能边界与实施默认值

这些是既定方向内的实施基线，Supervisor 可在不改变产品、安全或科研语义的前提下作 L0/L1 选择并记录。

- 通用模板覆盖原始 12 类科研对象；材料模板重点包含材料／样品、合成／表征实验、计算、Protocol、Dataset、Claim/Finding 与 MOF 合作案例。再以非材料通用模板完成一条网页案例。
- 模板允许项目级补充字段、说明、单位和校验；核心身份／版本／来源／权限规则不可移除。模板及记录历史不得随新配置就地变更，不承诺任意脚本、完整工作流设计器或公共模板市场。
- 预览首批必须覆盖文本／Markdown、PDF、常见图片、CSV/TSV 表格；其他格式至少可安全保存、按权限下载并说明暂不支持预览。额外格式由任务包明确支持清单与解析限制。
- 基础分析至少包含散点／折线／柱状图，计数／极值／均值／中位数／标准差，用户选择的线性与二次多项式拟合；保留列／范围／缺失值处理／单位／方法参数、来源版本、结果与导出。专业领域算法不由“通用科研”一词自动扩展。
- 上传容量沿用 docs/27 已有的 10GB 单 Blob 目标和分片设计；预览、表格读取、拟合计算另设有界资源限制，不能把整个大文件无界加载到浏览器／服务内存。资源参数在 M0/相关任务中实测记录；若既定容量无法满足，明确报告缺口，不偷偷降级完成标准。
- 单人自审、团队独立评审的具体 policy 与审核记录在 WEB-00 固化到契约；自审不伪装为独立验证。旧项目、旧附件、旧 Release 和组织更严政策维持原有效规则。
- 沿用原始 Fork/PR、Reference/Dependency 分离、贡献归属、Rights 与选择性发布；未声明使用授权不等于可任意重用。无须为本轮引入新的许可证或法律协议。
- 核心流程不依赖 AI provider、MCP、材料生成模型、仪器控制、HPC 调度、公共社交信息流、付费／赏金或跨组织保密 compartment。
- 团队试用版仍需基本安全、限流、错误处理、监控、备份恢复和配置检查；不以“不是公众 Beta”为由省略这些要求。

## 12. 开发组织与无人值守执行

采用长期 Supervisor＋独立完整 Claude Code Worker；先 1 个 Worker 验证模型、工具、隔离、RESULT、Review 与恢复，再按无冲突任务扩大到 2–3 个；默认上限沿用 3，硬上限 4。独立 Review Worker 与实现 Worker 共用并发资源。不得以 Claude Code subagent 替代独立 Worker。

Supervisor 直接编排现有 rddev 子命令，rddev drive 是可选机械执行器，见 ADR-029。取消强绑定没有取消 G1–G4、scope/HEAD 校验、Git 控制权限或长期恢复责任。普通工程失败由 Supervisor 调查、返工、重派／拆任务并继续；新的 L3、重大架构变化或新凭据才停止受影响路径并汇总必要输入。

每个可交付切片必须留下：需求／决定 → 正式 T 任务 → Issue → 分支与 Worktree → Worker/RESULT → 独立验收 → Commit → Push → PR → CI → Merge → 测试证据。只能由 Supervisor 创建分支、提交、推送、操作 Issue/PR 和合并。完整操作协议、模型预检和恢复规则见 docs/72。

产品里的“个人项目允许作者自审”不改变研发系统独立 G2/Review/G4 的要求。研发自动化与产品科研自动化是两件事；本轮只授权前者在既定规则内持续推进。
